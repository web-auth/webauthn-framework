WebAuthn PRF — client-side encryption demo

A minimal, dependency-free demo of the WebAuthn PRF extension, inspired by Matt Miller's 2023 write-up on encrypting data in the browser using WebAuthn.

⚠ Read this before you build a real product on PRF. Quoting Matt's May 2025 update to that article: “If you delete a passkey you will permanently lose access to all of its PRF-protected data. In such a scenario there is no way to recover PRF-protected data. It’s gone.” The PRF input-key lives inside the authenticator, never leaves it, and a re-created passkey produces a brand-new one — even with the same salt. This demo intentionally has no recovery path and is a learning aid only. A production design must escrow a recovery wrap, enroll a second passkey upfront, or surface an explicit “you will lose this data if you lose this passkey” contract.

The relying party server hands the browser a per-credential salt at every ceremony. The authenticator computes HMAC-SHA256(credentialBoundKey, salt) and the user agent surfaces the result as clientExtensionResults.prf.results.first. This demo derives an AES-GCM key from that PRF output via HKDF and uses it to encrypt (registration) and decrypt (authentication) a short note entirely inside the browser. The server only ever sees the ciphertext and the salt — never the key, never the plaintext.

Walk-through

  1. /register.html — register a credential with PRF support against the relying-party server.
  2. /vault.html — authenticate against the server, then encrypt & decrypt items of your choice. The AES-GCM key derived from prf.results.first and the HMAC key derived from prf.results.second stay in tab memory; reload to lock.
  3. /offline.html — same vault but without any server. Salts and ciphertexts live in localStorage; a service worker caches the page so you can hit airplane mode and reload.

What this demo deliberately leaves out

  • A real database / user system (uses a JSON file under var/).
  • Account recovery (lose the credential → lose access to the ciphertext, by design).
  • Key rotation: the salt is fixed per credential to keep the demo readable.
  • Cross-origin / multi-RP setups.
